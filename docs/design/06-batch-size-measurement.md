# 대기열 발급 배치 크기 산정

## TL;DR

대기열 발급 속도는 주문 API가 안정적으로 처리할 수 있는 수준보다 낮아야 한다.

부하 테스트 결과 주문 처리 한계는 다음과 같았다.

| 시나리오           |    한계 TPS | 병목       |
| -------------- | --------: | -------- |
| 여러 상품으로 주문 분산  | 약 550 TPS | DB 커넥션 풀 |
| 단일 인기 상품 주문 집중 | 약 150 TPS | 상품 row 락 |

이벤트 트래픽은 특정 인기 상품에 몰릴 가능성이 높다.
따라서 단일 상품 집중 시나리오를 기준으로 발급 속도를 산정한다.

최종 설정은 다음과 같다.

```yaml
admit-batch-size: 8
throughput-per-second: 80
```

100ms tick 기준으로 `batch-size: 8`은 초당 80명 발급을 의미한다.

---

## 1. 목적

대기열은 주문 API 앞에서 유입량을 조절하는 역할을 한다.

발급 속도가 너무 높으면 사용자는 대기열은 통과하지만, 주문 API 내부에서 DB 커넥션 대기나 락 대기로 인해 지연된다.
즉, 대기열의 목표는 사용자를 무조건 빨리 통과시키는 것이 아니라 **하류 시스템이 감당 가능한 속도로 통과시키는 것**이다.

이번 측정의 목적은 다음 값들을 실측으로 확인하는 것이다.

* 주문 API가 안정적으로 처리 가능한 TPS
* 병목 지점
* 대기열 발급 배치 크기

앱, DB, Redis, Kafka, k6가 모두 한 머신에서 실행되었다.
따라서 절대 TPS는 운영 환경에 그대로 적용하기보다, 병목 판단과 산정 방식의 근거로 사용한다.

---

## 3. 측정 방식

부하는 k6의 `constant-arrival-rate` 방식으로 주입했다.

서버가 느려져도 목표 TPS를 계속 유지하기 때문에, 어느 지점부터 지연과 드롭이 증가하는지 확인할 수 있다.

측정 시나리오는 두 가지다.

| 시나리오     | 설명             | 목적                |
| -------- | -------------- | ----------------- |
| 분산 주문    | 1만 개 상품에 주문 분산 | 커넥션 풀 기준 상한 확인    |
| 인기 상품 주문 | 하나의 상품에 주문 집중  | 상품 row 락 기준 하한 확인 |

주문 요청 1건의 주요 흐름은 다음과 같다.

```text
유저 조회
→ 멱등키 확인
→ 상품 FOR UPDATE
→ 재고 차감
→ 주문 저장
→ 주문 라인 저장
→ Outbox 저장
```

---

## 4. 측정 결과

### 4-1. 분산 주문

| 목표 TPS | 실제 TPS |   p95 |   p99 | 결과        |
| -----: | -----: | ----: | ----: | --------- |
|    100 |    100 |  16ms |  26ms | 안정        |
|    300 |    300 |  21ms |  31ms | 안정        |
|    500 |    500 |  45ms |  75ms | 한계 근접     |
|    700 |    695 | 457ms | 700ms | 커넥션 대기 증가 |
|   1000 |    543 |  3.2s |  3.6s | 처리량 하락    |

분산 주문은 약 550 TPS까지 처리 가능했다.

500 TPS까지는 안정적이었지만, 700 TPS부터 DB 커넥션 풀이 포화되며 대기 요청이 증가했다.

```text
분산 주문 한계 ≈ 550 TPS
병목 = DB 커넥션 풀
```

---

### 4-2. 인기 상품 주문

| 목표 TPS | 실제 TPS |   p95 |   p99 | 결과      |
| -----: | -----: | ----: | ----: | ------- |
|    100 |    100 |  33ms | 136ms | 안정      |
|    150 |    149 | 196ms | 371ms | 한계 근접   |
|    200 |    196 | 584ms | 673ms | 락 대기 증가 |
|    300 |    154 |  6.7s |  7.0s | 처리량 하락  |
|    500 |    141 |  8.9s |  8.9s | 붕괴      |

인기 상품 주문은 약 150 TPS부터 한계가 보였다.

동일 상품에 주문이 몰리면 상품 row의 `FOR UPDATE` 락 때문에 주문이 직렬 처리된다.
락을 기다리는 요청도 DB 커넥션을 점유하므로, 락 대기와 커넥션 풀 고갈이 함께 발생한다.

```text
인기 상품 주문 한계 ≈ 150 TPS
병목 = 상품 row 락 + DB 커넥션 풀 점유
```

---

## 5. 발급 속도 산정

이벤트 트래픽은 단일 인기 상품에 주문이 몰리는 상황에 가깝다.
따라서 분산 주문 기준인 550 TPS가 아니라, 인기 상품 주문 기준인 150 TPS를 기준으로 잡는다.

운영에서는 재시도, 네트워크 지연, 결제 호출, 순간 트래픽 증가가 발생할 수 있으므로 안전 마진을 둔다.

```text
인기 상품 주문 한계: 150 TPS
안전 마진: 70%
재시도 및 추가 비용: 1.3배

150 × 0.7 ÷ 1.3 ≈ 80 TPS
```

따라서 발급 속도는 초당 80명으로 산정한다.

현재 tick 주기는 100ms다.
즉, 초당 10번 발급한다.

```text
80 TPS ÷ 10 = 8
```

최종 배치 크기는 다음과 같다.

```yaml
admit-batch-size: 8
```

## 6. 기존 설정과 비교

| 항목                 |    기존 값 |        변경 값 |
| ------------------ | ------: | ----------: |
| `admit-batch-size` |      18 |           8 |
| 초당 발급량             | 180 TPS |      80 TPS |
| 기준                 |     추정값 |         실측값 |
| 적합한 상황             |   분산 주문 | 인기 상품 집중 주문 |

기존 값 18은 초당 180명을 발급한다.

분산 주문에서는 가능할 수 있지만, 단일 인기 상품 이벤트에서는 실측 한계인 150 TPS를 초과한다.
따라서 이벤트 기본값으로는 위험하다.

기본 설정은 `8`로 두고, 주문이 여러 상품으로 확실히 분산되는 이벤트에서만 `14~15` 수준까지 조정한다.

## 7. 상황별 권장값

| 상황                |      초당 발급량 | `admit-batch-size` |
| ----------------- | ----------: | -----------------: |
| 단일 인기 상품 이벤트      |      80 TPS |                  8 |
| 여러 상품으로 분산되는 이벤트  | 140~150 TPS |              14~15 |
| 트래픽 성격을 알 수 없는 경우 |      80 TPS |                  8 |

기본값은 보수적으로 `8`을 사용한다.

---

## 8. 결론

대기열 발급 속도를 높인다고 주문 처리량이 선형으로 증가하지 않는다.

하류 한계를 넘어서 발급하면 사용자는 대기열이 아니라 주문 API 내부에서 기다리게 된다.
그 결과 DB 커넥션 대기, row 락 대기, 응답 지연, 타임아웃이 증가한다.

이번 테스트에서 단일 인기 상품 주문은 약 150 TPS부터 한계가 나타났다.
운영 안전 마진과 재시도 비용을 반영하면 적정 발급 속도는 약 80 TPS다.

따라서 대기열 기본 발급 설정은 다음과 같이 결정한다.

```yaml
admit-batch-size: 8
throughput-per-second: 80
```

---

## 9. 추후 재측정 항목

운영 반영 전에는 아래 항목을 추가로 측정한다.

* 운영 DB 환경에서의 주문 API 한계
* 결제 API 포함 E2E 처리량
* Outbox Relay / Kafka 발행 부하
* 장시간 부하 테스트 시 GC 영향
* Redis 기반 재고 차감 적용 후 처리량 변화
